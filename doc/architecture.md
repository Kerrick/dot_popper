# Dot Popper's architecture

How Dot Popper's code is divided, what each part may depend on, and how a press, a frame and a save move through it. It is for anyone, person or coding agent, about to change the code. The words are `GLOSSARY.md`'s. Why each large choice was made is in the [decision log](adr/README.md); how each area works in detail is in the [design documents](#design-documents).

## The parts

Dot Popper is Ruby on [Lota](https://github.com/setdef/Lota), which runs LÖVE's engine with Ruby in place of Lua. The code is in four layers, the composition root that puts them together, an edge, and code outside the game.

| Part | Where | Holds | May use |
| --- | --- | --- | --- |
| **Core** | `lib/dot_popper/*.rb`, and `network/`, `groups/`, `continuity/`, `receipt/` | The rules (dots, the field, the score, the clock, spawning), the flow from Home to a game to Game Over (`Cabinet`), Stats and records, free games, Pro (`Entitlement`, `Receipt`, `Continuity`), the store port and its adapters (`Store`, `NativeStore`, `FakeStore`, `WebsiteStore`, `NoStore`), the HTTP client every request goes through (`Network`), when to ask the server again (`Refresh`), the friend-group client (`Groups`), the build's kind (`Build`), what the system means for the game (`Platform`), and the guard on automated runs (`Automation`) | Ruby's standard library only |
| **Use cases** | `lib/dot_popper/use_cases/` | What a player does that needs two of the game's areas: starting a game, finishing one, buying Pro, using a theme, joining a friend group, looking at achievements ([use cases](#use-cases)) | The core |
| **Presentation** | `lib/dot_popper/presentation/` | Everything a player sees, hears and presses that isn't a rule: every number, color, word, size, timing and animation (`Style`, `Words`), layout plans, effects, the tutorial, the sound synthesizer, input routing, the screens (`Screens`, one object for each, which answers its own input), and the `Show`, which ties them to the core's events and keeps the stack of screens | The use cases and the core |
| **Shell** | `lib/dot_popper/shell/` | Carrying the presentation out with Lota: painters, the `Renderer`, the `SoundPlayer`, gamepads, the Game Over pile's physics, save files, the clipboard, URLs, the store helper, `Engine`, which makes what the composition root asks of Lota, and `App`, which Lota's callbacks reach | The composition root, the presentation, the use cases, the core and Lota |
| **Composition root** | `lib/dot_popper/composition/` | `Composition::Root`, which builds the whole game for one platform and one kind of build from what the engine makes, and `Composition::DeveloperSettings`, the developer settings the build obeys ([composition](#composition)) | The presentation, the use cases and the core; never Lota |
| **Entry points** | `main.rb`, `conf.rb`, `bin/dot_popper` | `conf.rb` sets Lota's window and renderers before the window opens; `main.rb` hands each Lota callback to `Shell::App`; `bin/dot_popper` starts the game fused, for the phone builds | Everything |
| **Native code** | `ios/host`, `android/host`, `macos/store`, `windows/store` | Dot Popper's additions to Lota's phone hosts (the share sheet, the store, platform fixes), and the computer stores' helper programs | Their platform's APIs |
| **Outside the game** | `lib/dot_popper/privacy/`, `test/`, `sig/`, `script/`, `playtest/`, `.github/` | The privacy declarations and their generated document, tests, RBS signatures, the simulator and tools, playtest kits, CI | Anything |

### The rules between them

- **Only the shell calls Lota.** The core, the use cases, the presentation and the composition root name Lota only in comments, so all of their tests run without a window (`AGENTS.md` makes this a rule), and the engine's own names for things (a system's name, among others) stop at the shell. Code that needs the engine to decide something, such as measuring text, takes it as an argument: the presentation measures with whatever it is given (`Shell::FontMeasure` in the game, `RoughMeasure` in tests).
- **Dependencies point inward.** The core names nothing in the use cases, the presentation or the shell; the use cases name nothing in the presentation or the shell; the presentation names nothing in the shell; the composition root names nothing in the shell, which hands it what it needs. `lib/dot_popper/privacy/` is the exception, by design: it is not loaded by the game, and reads the presentation's words to write the privacy document.
- **The core is mostly values.** Dots, the `Stack`, the field, the clock (`Countdown`), spawns, `GameStats`, Stats, the rules' numbers and every event are immutable `Data` values, frozen deeply enough to be shared between Ractors (`test/ractor_test.rb`), and changes return new values. A few objects change in place, each by swapping in new values: `Cabinet`, which holds the current state and is the one object players' presses reach; the `Game` it holds while a game is paused, in play or just over; the keepers of what is saved (`ScoreRecord`, `StatsBook`, `StatsBackup`, `Achievements`, `FreeGames`, `Entitlement`); and the listeners that count a game as it plays (`AchievementRecorder`, `GameStats::Recorder`, `GamesLog`).
- **The core and the use cases are typed.** Steep checks `lib/dot_popper.rb`, `lib/dot_popper/*.rb`, `lib/dot_popper/use_cases/*.rb` and friend groups, `lib/dot_popper/groups/*.rb`, against `sig/` in strict mode ([ADR-0004](adr/0004-steep-checks-the-rules-strictly.md)). The presentation, the composition root, the shell and the core's other subfolders are not typed.
- **Every outside party is behind a port.** The network is reached only through `Network::Link`, by a request made only from its declaration ([privacy](design/privacy.md#requests)); a store only through the store port, `Store` ([ADR-0009](adr/0009-the-store-is-a-port.md)); a file only through `Shell::SaveFile`; the system's share sheet and stores only by a URL the host catches or a helper process ([ADR-0008](adr/0008-native-features-live-outside-the-ruby-process.md)). Tests source-scan for the first and third ([ADR-0014](adr/0014-privacy-facts-come-from-the-code.md)).
- **The build decides what it trusts.** `Build::CHANNEL` is nil in a test build (every playtest kit and CI run) and names a store in a store build. It alone chooses the store's adapter, the keys and receipts trusted, and which `DOT_POPPER_*` settings are obeyed ([ADR-0010](adr/0010-pro-comes-only-from-proof.md)). Monetization decides each from the channel, in the core (`Store.for`, `Continuity.pins_for`, `Receipt.trusted`, `Continuity::License.kept_in`, `FreeGames.metered?`); the composition root asks and connects what they answer, and `script/check_build.rb` asks the same of a built app. The game reads the environment only through `Build.settings`, which `Composition::DeveloperSettings` wraps.
- **Automated runs reach no outside host.** A test, a GUI scenario, the bot, or any run told to quit or take screenshots by itself sets `Automation.on?`, and `Automation.guard!` then refuses every connection to a host that isn't this machine.

## The game as a state machine

`Cabinet` (`lib/dot_popper/cabinet.rb`) is the game as a whole. Its state is one of four values, `Home`, `Paused`, `Playing` and `GameOver`, each answering `press(x, y)` and `update(seconds)` with the state that follows. A press on Home reaches no rule: a game begins only when it is started, through the cabinet's `Cabinet::Starts` (`#game`, or `#paused` for the tutorial), which `Cabinet#starts` hands out once and the composition root gives `UseCases::StartGame`, so nothing else is handed the means to start one: the cabinet has no method of its own that starts a game (`test/cabinet_test.rb`), and `test/use_cases/start_game_test.rb` fails if any other file in the game's code takes the Starts or reads them by reflection (`@starts`). Ruby cannot forbid reflection, so a name spelled at run time would pass that scan. The game is a `Game` (`lib/dot_popper/game.rb`): the field, the `Stack` of dots, the `Countdown`, the score, and the `Spawner`. Only `Cabinet` holds it; its states, and anyone who asks (`Cabinet#game`), get its read-only `Game::View`, made once with the game, which answers what the game is and nothing that changes it, so the screens, the renderer, the bot and the tutorial read the game each frame without being able to change it (`test/cabinet_test.rb` fails if anything the cabinet answers can). Only a press at a place reaches the game, so no key or gamepad button can touch the score or the clock, and nothing outside `Playing` changes either, except a `Paused` game while the tutorial plays over it.

Each change is announced as an event (`lib/dot_popper/events.rb`): `Popped`, `Penalized`, `Missed`, `GameStarted`, `GameEnded`, `HomeShown`. An event is a value made after the change, carrying what a listener needs of the game as it then stood, under `Game`'s own names (the field, the dots, the score, the countdown, the time played, the row), and never the `Game` itself: a listener reads the game from its events alone, so one that keeps an event never sees later play through it (`test/ractor_test.rb` fails if any event can't be shared). `Cabinet` tells every listener in order. Nothing in the core, the use cases, the presentation or the composition root subscribes itself: the composition root subscribes `UseCases::FinishGame` (which passes each event to its `GameStats::Recorder` and `AchievementRecorder`), then the `Show`, `Refresh` and `GamesLog` (`games.csv`), and the shell's `App#load` then subscribes the `Pile`, `Tilting` and `Dragging`. In the shell, `Shell::DevelopmentHooks` subscribes itself as it is made, when a development setting asks it to meter frames. A listener that holds the `Cabinet` can read the game as it stands (`Cabinet#game`, a `Game::View`) but not change it.

Screens other than Home, a game and Game Over (Settings, Stats, Achievements, Themes, Friend groups, the Pro offer, Credits, Privacy, the share preview, the tutorial) are the presentation's alone: each is a screen object (`Presentation::Screens`) that the `Show` opens on its stack over Home or Game Over, and the one on top answers every input ([ADR-0018](adr/0018-screens-are-objects-on-a-stack.md)); a press there never reaches `Cabinet`. The tutorial is the exception: it is a layer over a real game, which `Cabinet` holds `Paused` before its clock first runs (`Cabinet::Starts#paused`). The tutorial moves that game's dots at its own pace and passes it only the presses it chooses (`Cabinet#press_paused`, whose events come back to it and are announced to no one); when it ends or is skipped, the same game plays on (`Cabinet#unpause`, which announces `GameStarted`; [ADR-0016](adr/0016-the-tutorial-is-a-layer-over-a-paused-game.md)). Every way into a game, Play or the tutorial's opening, goes through `UseCases::StartGame`, which spends a free game ([ADR-0012](adr/0012-free-games-20-then-3-a-day.md)).

## Use cases

The game's domain is in three areas, the maintainer's division ([ADR-0019](adr/0019-clean-architecture-and-domain-driven-design-in-three-areas.md)): Gameplay and Metagame (playing, Stats, records, achievements, today's goal, friend groups and the title, themes), Monetization (Free and Pro, free games, locked features, the stores, receipts, license keys, proof that setdef is there), and Release Engineering. The folders are not divided by them yet. The rules of play never know that Pro exists, so a rule that needs both of the first two lives in a use case (`lib/dot_popper/use_cases/`, `DotPopper::UseCases`), outside both and outside the screens ([ADR-0017](adr/0017-use-cases-hold-the-rules-that-need-two-areas.md)). Each is an object made with its collaborators by the composition root (`Composition.use_cases`, which also subscribes each to what it hears), handed to the `Show`, and called from a screen (all but `FinishGame`, which hears the rules' events instead), whose screen carries out what it answers rather than deciding beforehand; each is tested in `test/use_cases/` with memory stores and local fakes. The `Show` and its screens are never given what decides Pro (`Entitlement`, `FreeGames`, the stores, `Continuity::License`), only the use cases that ask it, and only the offer of Pro (`Screens::Offer`) is given `BuyPro`. `test/use_cases/pro_knowledge_test.rb` walks the game as the root builds it and fails if anything in the presentation holds one of those, outright or in a block it keeps; and, as a second line, fails if anything in `lib/` outside Monetization's own code, the use cases and the composition root names them or asks `pro?`. Neither sees a constant or a global reached by a name spelled at run time.

| Use case | Does | Takes | Answers |
| --- | --- | --- | --- |
| `StartGame` | Starts a game from Home and spends one free game on it: in play at once for Play, or paused with the tutorial's first dot (`Tutorial.opening`) for the tutorial, which is spent as it opens. With none left nothing starts, and the `Show` opens the offer of Pro. | `Cabinet`, `FreeGames` | `:started`, `:none_left`, or `:not_home` away from Home; `#none_left?` says beforehand whether Play would lead to the offer, for Play's word and Game Over's Play again; `#left` and `#daily` how many games are left and come each day, nil where none are counted |
| `FinishGame` | Hears the rules' events, counting each game's numbers (`GameStats::Recorder`) and the achievements its play earned (`AchievementRecorder`), and finishes a game as `GameEnded` is heard: adds it to Stats with the records it set and today's goal, keeps the achievements it earned for anyone, tells friend groups of a game that counts (never one the tutorial opened, which `GameEnded#tutorial` says), and, for Pro alone, reports its new achievements and lets Game Over show them. | `StatsBook`, `Achievements`, `Entitlement`, the friend-group session | what Game Over shows, told to its listeners (`#subscribe`) as each game is finished (`FinishGame::Finished`: the game's `GameEnded`, its numbers, and the record set, the goal met and the achievements to name); and the numbers of the game in play (`#stats`) |
| `BuyPro` | The offer's actions: asks the store as the offer opens; Buy, or Try again before a price has come; Restore Purchases; a license key pasted or typed. Buy and a typed key do nothing once the player has Pro. Hears the store only while no game is in play, and when Pro arrives reports the achievements already earned to friend groups. The offer's one way to the store and to Pro. | the store port (`DotPopper::_Store`), `Entitlement`, `Cabinet`, `Achievements`, the friend-group session | whether Pro is offered or owned, whether Buy was taken, and what the offer shows of the store: whether it sells, takes a key, its price, its status and the key typed so far |
| `UseTheme` | Uses a theme the player chose, if they have Pro and it is open; says which theme is current (a Pro player's choice, the ordinary one for Free), taken up only between games. | the `ThemeKeeper`, `Entitlement` | `:used`, `:same`, or `:offer` for a Free player |
| `JoinOrCreateFriendGroup` | Joins or creates a friend group for a Pro player; leaving and deleting never need Pro, so they are not here. | the friend-group session, `Entitlement` | `#start` (as Join or Create is pressed, before the notice or the code pad) `:go`, `#join` and `#create` `:sent`, each `:offer` for a Free player, which the friend groups' panel acts on |
| `ViewAchievements` | Says what the Achievements screen and its dialog may show: for Pro which are earned, the day, how many, and how far along the four measured ones are; for Free none of it. | `Achievements`, `Entitlement`, `StatsBook`, `ScoreRecord` | each of those, or nil while locked |

The `Show` lays out Game Over when `FinishGame` tells it a game is finished, not when it hears `GameEnded` itself, so what Game Over shows is the game's own whatever order the listeners hear the rules in (`test/presentation/show_test.rb` has a `Show` hear them first). The score record is judged by `Cabinet` as the game ends and carried by `GameEnded`, as before: a record is the same area as the game, so no rule of Pro is in it, and moving it would change what `GameEnded` carries for every listener with no rule gained.

Changes that another area cares about are announced by the object that knows, rather than found by the `Show` comparing before and after: `Entitlement` announces `Entitlement::ProGranted` when Pro arrives ([store and Pro](design/store-and-pro.md#the-storefront-port)), and `Continuity::Gone` announces `SetdefGone` or `SetdefHere` with each check it takes up, which `ThemeKeeper` and `ServerChoice` hear ([when setdef is gone](design/store-and-pro.md#when-setdef-is-gone)).

`StartGame` spends in the same call that starts the game, before it starts, as the `Show` did. Spending as an echo of the game's own `GameStarted` was weighed and set aside: a game the tutorial plays over announces `GameStarted` only as play begins, after the tutorial, but is spent as it opens (ADR-0016), so the echo would move the spend, or need an event the rules make only for Monetization.

## A frame

Lota calls `main.rb`'s callbacks; each goes straight to `Shell::App` (`lib/dot_popper/shell/app.rb`).

1. **Inputs.** Each input callback (a mouse, a finger, a gamepad's button or trigger, a key, the wheel, focus) goes to `Shell::LotaInput`, which turns it into the game's own event (`Presentation::MousePress`, `ButtonPress`, `KeyPress` and the rest) by the game's names, and `App` hands that to its one entry point, `Presentation::InputHandler#call`. The shell decides nothing about what an input means. The handler does: `Chatter` drops a failing mouse's double click; `InputRouter#tap` leaves out what is no press of the player's own (SDL's made-up mouse for a finger, a mouse's side buttons, a trackpad's touches) and turns the rest into a `Tap`; a `Tap` goes to `Show#tap`, which hands it to the screen on top (`Show#screen`): a button's, empty space's, the tutorial's, or a game's, which passes it to `Cabinet#press` on the frame it happened; on Game Over a press away from the buttons goes to the pile instead (`Shell::Dragging`). A gamepad's A presses at its cursor through the same path; its other buttons, the keys and the wheel go to what the screen on top answers (`Show#pad`, `#primary`, `#back`, `#type_key`, `#scroll_key`), in the order `doc/design/input.md` gives. What only the engine can do (the splash, quitting, fullscreen) the handler asks of the `App`.
2. **Time.** `Lota.update` calls `App#tick`, which measures the time between the last two frames starting to draw (`FrameClock`), not Lota's own `dt`, and clamps it to `Rules::LONGEST_FRAME` (0.1 seconds).
3. **Update.** `App#update` hands the sticks to the `InputHandler`, which moves the gamepad cursor (or scrolls a list), then moves the bot if it plays, `Cabinet`, the `Show` (its effects, animations, HUD, the screens' state, the store's answers through `UseCases::BuyPro`, and the friend-group session), the theme feed and the setdef watch, then the shell's tilt, drag, pile physics and particles, and, where a development setting asks for them, the screenshots, the quit and the frame meter (`Shell::DevelopmentHooks`).
4. **Draw.** `Lota.draw` calls `Renderer#draw`, which draws the `Show`'s state through the `Pen` and the painters straight to the window at its own pixels: the night, the dots and their glow (or the pile after time's up), effects, Game Over's words and the HUD, then the screens open over the game's state from the last that covers the rest up to the top one (`Show#layers`), and the gamepad cursor.

The GUI scenarios replace step 2 with a fixed step and push presses onto Lota's event queue, so everything else runs as a player's game does ([ADR-0005](adr/0005-gui-scenarios-play-the-real-game.md)).

## Composition

`Composition::Root` (`lib/dot_popper/composition/root.rb`) is the composition root. It decides, in plain Ruby with no Lota, what the game is built from on its `Platform` and in its kind of build (`Build::CHANNEL`), and builds it: it has the window opened (a phone's screen filled, a computer's window sized), makes every save file's store, the `Cabinet` with its `ScoreRecord`, `StatsBook`, `Achievements` and `StatsBackup`, the `Entitlement` with the pins and receipts Monetization trusts for the channel (`Continuity.pins_for`, `Receipt.trusted`), the license key's save file where Monetization keeps one (`Continuity::License.kept_in`), the setdef watch, the store for this build (`Store.for`), `FreeGames`, metered as `FreeGames.metered?` says, the friend-group `Session` and the server it uses, the `ThemeKeeper`, `UseCases::UseTheme` (which the `Pen` and the `SoundPlayer` take the current theme from at launch), the other use cases (`Composition.use_cases`), the `ThemeFeed`, haptics and sharing for the platform, the splash, the `Show`, which takes the use cases and the presentation's own collaborators as arguments, the games log, the gamepad cursor and the bot. It subscribes every listener it makes itself, and nothing it makes subscribes itself: `FinishGame` to `Cabinet` and `BuyPro` to `Entitlement` (in `Composition.use_cases`); then the `Show` to `Cabinet` and to `FinishGame`, which tells it each game it finishes for Game Over, and the offer of Pro to `Entitlement`, so a purchase ticks on it after friend groups are told; the `ServerChoice` and the `ThemeKeeper` to `Continuity::Gone`; and `Refresh` and the playtest log to `Cabinet`. `test/composition/root_test.rb` checks the order, that making a `Show` subscribes nothing, and that the `Show` it builds lays out the Game Over of a game played there. Nothing it makes reaches past the process until `Root#start` (the theme feed's first request, the store's first question, the setdef watch).

What only the engine can make or do, the root asks of an engine it is given, whose methods it lists: a save file by name, what a graphics unit is called, the window's size and layout, opening the window, the `Pen`, the `SoundPlayer`, text measure, the clipboard, the URL opener, the vibration motor, the notices, the store helper and the store's answer file. In the game that is `Shell::Engine`. The developer settings it obeys are `Composition::DeveloperSettings`, the environment as the build allows (`Build.settings`), which `Shell::App` makes once.

`Shell::App#load` makes the `Engine` from the `Platform` the shell makes of `Lota::System.os` (`Shell::Platforms`), hands it to the root, and then makes only what carries the game out with Lota: the Game Over `Pile`, `Gamepads`, `Tilting`, `Dragging`, the particles and the `Renderer`, in the styles the root chooses. `test/composition/root_test.rb` builds the root for every system and every channel, with memory stores and a fake engine (`test/composition/fake_engine.rb`), and checks each of those choices; presentation tests build a `Show` as the root does, through `PresentationTest.show`, with memory stores in place of files.

`conf.rb` runs before all of this, and before the window opens: it names the save folder (`t.identity`), sets the window, and chooses the renderers, with the rescue that starts the game again without Vulkan when Vulkan can't start it ([ADR-0007](adr/0007-renderers-per-platform-with-a-relaunch-without-vulkan.md)).

## Saving

Everything the game keeps is a text file in Lota's save folder, read and written whole through `Shell::SaveFile`, which refuses any name not declared in `Privacy::SAVE_FILES`. Lota's save folder can't rename or append, so a file is rewritten whole, and a backup is a copy written before the original changes. The core's keepers (`ScoreRecord`, `StatsBook`, `FreeGames`, `License` and the rest) each take a store that answers `read` and `write(text)`, so they work on a memory store in tests. Saves read leniently: a line that can't be read keeps its starting value. `doc/privacy.json` lists every file, what it holds, and what leaves the device.

## Threads

The game runs on Lota's one thread. Friend groups' requests and the theme feed's each run on a `Network::Worker`'s thread, at low priority, started by its first request, so a player with no friend group has no thread for them; the setdef watch has a thread of its own. A frame reads finished replies and never waits. The simulator and one test use Ractors; the game does not.

## Platforms

One code base runs on macOS, Windows and Linux (built by `lota fuse`, [ADR-0006](adr/0006-lota-fuse-builds-the-desktop-apps.md)) and on iOS, iPadOS and Android (built by Lota's phone guide with Fledge). The shell makes one `Platform` value from Lota's name for the system (`Shell::Platforms`), and everywhere else the game asks it its own questions (is this a touch device, does it quit itself, does it buzz, which store is its own), so nothing beyond the shell names a system. The differences are in a few places: `DotSize.for`, `Entitlement.forced?`, `Shell::Haptics`, `SheetSharing.for` and `Store.for` by platform; `conf.rb`'s renderers; the phone hosts' native files; and the desktop's window controls (`Shell::DesktopWindow`). [Platforms](design/platforms.md) has the details.
